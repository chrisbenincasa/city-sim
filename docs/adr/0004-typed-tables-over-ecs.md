# Entities are rows in typed tables, not components in an ECS

**Every entity — Citizen, Household, Building, Business, Lane, Trip — is a row in a typed struct-of-arrays table, addressed by a generational handle `{index: u32, generation: u32}`. There is no ECS: no component registry, no archetypes, no query planner, no scheduler.** Each table is hand-written, split into a hot half and a cold half, and iterated in index order.

## Why

An ECS earns its complexity through **heterogeneous composition** — when the set of entity types is open, unknown at compile time, or combinatorially large, and the framework's real job is to answer *"give me everything with A and B but not C"* over a layout nobody wrote by hand. That is a genuine problem and an ECS is a good answer to it.

We do not have that problem. A city simulation's population is **homogeneous**: every Citizen has the same fields as every other Citizen, permanently. There are perhaps 8–15 entity types in the entire design, all of them known at compile time, none of them composed at runtime. The query never varies, so a query engine has nothing to decide. Paying a framework tax on every type to buy a generality we can enumerate on two hands is precisely the shape of mistake that cost Citybound its simulation: `kay` imposed a `Compact` constraint on every type and generated code in every module to buy transparent multi-core parallelism that was never collected.

Four things a hand-written table buys that are worth more here than composition ever would be:

- **Serialisation is array dumps.** A save is a per-table header plus a block copy per column. No reflection, no schema walking, no object-graph traversal, and — because the layout is the file format — no divergence between what is simulated and what is persisted. Migration is a version number on the header. `FAST ITERATION`
- **Total control over iteration order, and therefore determinism.** An ECS's iteration order is a function of archetype layout, entity creation history and internal chunking. All of that is correct; none of it is something we chose, pinned, or can reason about when a State Hash diverges.
- **No framework upgrade silently reorders anything.** A determinism regression caused by a dependency bump is the worst kind of regression, because our code did not change and bisecting finds nothing.
- **No engine coupling**, which is load-bearing for [`0002`](0002-simulation-is-an-engine-agnostic-library.md) rather than merely tidy. Tables are plain arrays in a plain .NET library, so the simulation can be run headless, benchmarked in isolation, or ported wholesale.

## Rejected

**Unity DOTS** specifically — not Unity, DOTS — because adopting it welds the simulation to one engine and one engine version, directly contradicting [`0002`](0002-simulation-is-an-engine-agnostic-library.md). Its performance argument is real, but the memory layout it works hard to produce is the layout we are writing by hand anyway.

**A general table framework of our own**, with codegen, reflection and a component-like API. This is the yak-shave version of this decision, and it is how ten dead libraries get written instead of one game. Tables here are written once per entity type, by hand, in the file that owns them. Repetition across 8–15 types is cheaper than any abstraction that would remove it.

> **One deliberate step onto this slope, taken in [`0003`](0003-deterministic-integer-simulation.md) and kept small.** Every field is declared once as either `(saved AND hashed)` or `(derived AND rebuilt)`, and the save serialiser and State Hash are generated from that one declaration. This extends *"the layout is the file format"* above by a single step, and it exists because of a defect class that otherwise has **no detector at all**: a field that is saved but not hashed is invisible to every tool in the project — two runs diverge on it, the hashes agree, replay reports success, and the save/reload test passes because the field *is* saved. **A per-field flag is not a framework**: no reflection, no component API, no query planner, and the tables stay hand-written. The line this ADR is defending is *generality nobody asked for*, and this is not that.

## Consequences

- **Hot/cold splitting is explicit and decided per table.** The hot half holds what is touched on an ordinary Tick; the cold half holds everything else. The concrete case that drove this: **Household economics** — income, expenses, savings, purchases made and purchases missed — belongs in the cold table, touched only when a Household transacts or when the UI inspects it. This is what makes "ship with role and routine, leave room for economics" real rather than aspirational: the later layer extends a cold table instead of restructuring a hot loop.
- **It makes [`0003`](0003-deterministic-integer-simulation.md)'s "never iterate a hash map" practical rather than merely aspirational.** A prohibition only holds if there is somewhere better to go, and dense arrays indexed by handles are that somewhere: index order *is* iteration order, it is identical across runs and machines, and it is the fastest option as well as the correct one. The two decisions hold each other up.
- **Handles, not references.** The generation counter turns use-after-free into a detected error: a stale handle whose generation no longer matches the slot is rejected rather than silently reading a recycled row. In a deterministic simulation this matters more than usual, because a dangling read is a divergence, not a crash. Handles are typed as well as generational, so a Citizen handle cannot index the Building table — a class of bug an untyped `Entity` id leaves open by construction.
- ~~**The Past/Future double buffer is a block copy.** Two world states are two sets of arrays, and advancing a Tick is a bulk copy of the hot columns plus writes into the Future.~~ **Struck by [`0037`](0037-the-world-is-single-buffered-and-hazards-are-per-table.md).** The point that survives is the one about archetype stores: under one, the same guarantee would mean cloning a structure whose layout we do not own, and SoA makes any snapshot a block copy of arrays we do.

    > **This was a buffering strategy, not a layout consequence, and it should never have lived here.** At 1M it was a **~150 MB copy per Tick** against ~1 MB of actual writes — 8–15 ms, memory-bandwidth bound, and it **cancelled the Event Wheel** by touching every sleeping Citizen every Tick. `0037` replaces it: one live state, with double buffering only where a *parallel* phase both reads and writes a table (Lane dynamics and Map Layer cells, ~2 MB total). **This ADR's layout claim is untouched** — the third instance of a decision riding into the design inside an ADR about something else, after `0001` (the core's language) and `0002` (an unnamed query surface).
- **Referential integrity is ours to maintain.** A Building's Occupant, a Household's dwelling, a Trip's Legs — no framework enforces these, so the owning table's code does, backed by invariant tests that walk every cross-table handle after a run.
- **Adding a field means editing a table**, which is more typing than adding a component and is accepted. With 8–15 types the total cost is bounded and known.
- **Tables partition naturally along Chunks**, which is the same partition used for dirty tracking, saving and parallel work assignment. Keeping the storage layout and the spatial partition aligned is free here and would be awkward to arrange through an archetype store.

    > **True for static entities, unargued for mobile ones — flagged by [`0037`](0037-the-world-is-single-buffered-and-hazards-are-per-table.md), not yet closed.** Buildings, Lots and Lanes have fixed positions and partition cleanly. Grouping **Households or Citizens** by home Chunk means a Household moving house **relocates its row**, and a relocated row is worse than a stale one: `05 §3`'s generation counter detects use-after-free, but it cannot detect *this handle now points at someone else's valid row*. Either rows never move and the Chunk partition is a separate index, or rows move and every handle needs indirection. `05 §5` role 3 (parallel work assignment) leans on this claim and it is owed an answer.

## What would trigger revisiting

- **Genuine heterogeneity appearing** — many entity types with wildly differing field sets, or behaviour that must be composed at runtime from combinations we cannot enumerate at compile time. The honest symptoms are a table whose fields are meaningful for only a small fraction of its rows, or a proliferation of near-duplicate tables differing by a column or two. This is something to watch for rather than pre-empt. Even then the first answer is splitting the table or adding an optional side table; a full ECS is the answer only if that stops working.
- **Not performance.** Hand-written struct-of-arrays is the layout an ECS exists to produce, so an ECS cannot beat it in kind — only in optimisation detail we are free to copy directly.

    > **This trigger is correct about layout and it made something else unchallengeable.** The Past/Future block copy above was a **performance** defect living inside an ADR that had declared performance out of scope, so the only ground on which it could be attacked was foreclosed by a sentence about ECS. It went unnoticed for eight sessions and was found by accident while sizing an unrelated question. Same species as `0002`'s revisit trigger having already fired on the day it was written. **The general check: a revisit trigger protects the decision its author had in mind, so run every trigger against what the ADR actually decided rather than against what it is titled.**
